## 2. โมดูลที่ทำการทดสอบ

โมดูลการประเมินใช้รูปแบบการตรวจสองเฟส ซึ่งพัฒนาขึ้นตลอด bolt 006–023 ดังนี้

1. **เฟสที่ 1 — บันทึกผลตรวจรายข้อ** ผู้ประเมินที่มีสิทธิ์ในหมวดนั้นบันทึก `approve`, `change_score` หรือ `reject` ต่อคำตอบหนึ่งข้อ โดย `approve` จะเขียนสถานะ `recommended` เสมอ และไม่เขียน `finished` ไม่ว่ากรณีใด รวมถึงกรณี ODPC (ข้อบังคับ FR-5) เส้นทางนี้ไม่เปลี่ยนสถานะ Cover และไม่ส่งอีเมล
2. **เฟสที่ 2 — การสรุปผลโดย ODPC** ผู้ประเมินระดับ ODPC หรือผู้ดูแลระบบ DOED สรุปผลทั้ง Cover โดยคำตอบที่เป็น `recommended` และไม่ถูกแก้ไขทับจะถูกเลื่อนเป็น `finished` ไฟล์ของคำตอบที่ถูกปฏิเสธ ณ ขั้นสรุปผลจะถูกลบ มีการเขียน `coverLogs` หนึ่งรายการ (`finished` หรือ `in_progress`) คำนวณ Grade เมื่อ Cover เสร็จสมบูรณ์ และส่งอีเมลแจ้งโรงงานหนึ่งฉบับเท่านั้น

เส้นทาง API แบบชุด (batch verdict) และ `VerdictBatchSchema` เดิม ถูกลบออกแล้วใน bolt 021

## 9. การประเมินความครอบคลุม

**ครอบคลุมดี** เส้นทางการเขียนแบบสองเฟสเป็นส่วนที่ทดสอบละเอียดที่สุดในระบบ ครอบคลุมผลลัพธ์ของแต่ละคำวินิจฉัย ข้อบังคับ FR-5 การตรวจสิทธิ์ผู้บันทึกเดิม ขอบเขตหมวดและเขต เงื่อนไขปิดกั้นการสรุปผล การบันทึกเจ้าของการเลื่อนสถานะ ผลลัพธ์ทั้งสองแบบของ Cover การเลือกและเนื้อหาอีเมล การลบไฟล์แบบเลื่อนเวลารวมถึงการยกเลิกเมื่อ MinIO ล้มเหลว และความเป็นอะตอมมิกของทรานแซกชัน โดยตรวจครบทั้งฝั่งผู้ประเมินและฝั่งผู้ดูแลระบบ

**ครอบคลุมบางส่วน** การคำนวณ Grade มีการทดสอบเชิงคำนวณและเชิง schema แต่การเชื่อมกับการสรุปผลตรวจเพียงว่าค่าที่ได้อยู่ในชุดค่า Grade ที่ถูกต้อง มิได้เทียบกับค่า Grade ที่คาดหวังแน่นอนต่อชุดข้อมูลตั้งต้น ส่วนการผูกเส้นทาง API ครอบคลุมเพียงการลงทะเบียนและการผูก guard

**ยังไม่ครอบคลุม** เส้นทางปฏิเสธสิทธิ์ตามบทบาท (D-01) การต่อรองของโรงงานและเงื่อนไขการส่งซ้ำซึ่งยังเป็นการทบทวนโค้ดจาก bolt 009 การทำงานพร้อมกัน เช่น การสรุปผลพร้อมกันสองครั้งและการส่งซ้ำซ้อน ความเป็น idempotent และการสรุปผลซ้ำ (D-02) พฤติกรรมจริงของ MinIO, Redis, การประมวลผล BullMQ และ SMTP ซึ่งถูกแทนที่ด้วย stub ทั้งหมด รวมถึงพฤติกรรมช่วงรอยต่อปีงบประมาณของคำสั่งค้นหา Cover ที่โมดูลนี้เรียกใช้

## 10. สรุปผลและข้อเสนอแนะ

**สรุปผล** ตรรกะทางธุรกิจของโมดูลการประเมินอยู่ในสถานะผ่านการตรวจสอบ ณ การรันครั้งล่าสุดที่บันทึกไว้ คือ **ผ่าน 51 จาก 51 กรณีหลัก เมื่อวันที่ 7 กรกฎาคม 2569** โดยไม่มีข้อบกพร่องค้างในตรรกะของโมดูล และมีการสอบทวนย้อนกลับตามเกณฑ์การยอมรับครบถ้วนสำหรับ bolt 019–023 ระดับความเชื่อมั่นในเส้นทางการเขียนข้อมูลจึงอยู่ในเกณฑ์สูง ขณะที่ความเชื่อมั่นด้านขอบเขตสิทธิ์ พฤติกรรมเมื่อทำงานพร้อมกัน และการเชื่อมต่อบริการภายนอกอยู่ในเกณฑ์ต่ำ ทั้งนี้ตัวเลขทั้งหมดในรายงานยังไม่ได้รับการตรวจสอบซ้ำ ณ วันที่ 17 สิงหาคม 2569

**ข้อเสนอแนะ เรียงตามลำดับความสำคัญ**

1. จัดเตรียมฐานข้อมูลสำหรับทดสอบที่ใช้แล้วทิ้งได้ ผ่านการ migrate และ seed พร้อมกำหนด `TEST_DATABASE_URL` และการตรวจชื่อฐานข้อมูลแบบปิดกั้นไว้ก่อน จากนั้นรันชุดทดสอบหลักทั้งสี่เพื่อปรับค่าอ้างอิงของรายงานฉบับนี้ (D-05)
2. เพิ่มการทดสอบ e2e แบบยืนยันตัวตน เพื่อยืนยันผล 403 สำหรับ token ที่มิใช่ DOED และ 401 สำหรับผู้ไม่ยืนยันตัวตนบนเส้นทางฝั่งผู้ดูแลระบบทั้งสอง เพื่อปิดเกณฑ์ที่ค้างจาก bolt 011 และ 012 (D-01)
3. ดำเนินการ bolt 024 ให้เสร็จสิ้น โดยรันกรณีทดสอบทั้ง 5 รายการ สะสางประเด็นข้อมูลตั้งต้นใน `score.integration.test.ts` และจัดทำรายงานผลการทดสอบ (D-03, D-07)
4. ตัดสินใจเรื่องการสรุปผลซ้ำอย่างชัดเจน โดยเพิ่มกลไก idempotency หรือบันทึกพฤติกรรมปัจจุบันไว้ในภาคผนวกของ ADR (D-02)
5. เพิ่มกรณีทดสอบที่รันได้สำหรับการต่อรองของโรงงานและเงื่อนไขการส่งซ้ำ ซึ่งเป็นส่วนที่ยังใช้การทบทวนโค้ดเพียงอย่างเดียวมากที่สุดในกระบวนการประเมิน
6. ทำให้การตรวจชนิดข้อมูลทำซ้ำได้ และเพิ่มคำสั่ง lint แบบอ่านอย่างเดียว ก่อนกำหนดให้ทั้งสองรายการเป็นด่านคุณภาพใน CI (D-10)

## 11. คำสั่งสำหรับตรวจสอบซ้ำ

**ห้าม** รันคำสั่งเหล่านี้จนกว่าจะยืนยันได้ว่า `DATABASE_URL` ชี้ไปยังฐานข้อมูลที่ใช้แล้วทิ้งได้ ผ่านการ migrate และ seed แล้ว

```bash
# ชุดทดสอบหลักของโมดูลการประเมิน
bun test src/service/evaluator-review.integration.test.ts
bun test src/service/evaluator-review.save.integration.test.ts
bun test src/service/evaluator-review.standards.integration.test.ts
bun test src/service/evaluator-review.verdict.integration.test.ts

# ชุดทดสอบข้างเคียง
bun test src/service/answer.integration.test.ts
bun test src/service/score.integration.test.ts

# รันได้โดยไม่ต้องใช้ฐานข้อมูล
bun test src/service/score.test.ts

# ตรวจ lint แบบอ่านอย่างเดียว
bun ./node_modules/.bin/biome check src
```
