Dev OTP Bypass — How-To

Log in as any staff role locally without the email-OTP second factor — gated by a secret header, master-switched by an env flag, and structurally impossible in production.

What it is

Staff roles (DOED, Evaluator, Provincial) must pass an emailed one-time passcode after their password (see the staff 2FA flow). That makes the email worker a login-critical dependency — inconvenient for local development and QA.

This bypass lets a developer skip only the OTP step by sending a secret header on POST /twhp/api/authentication/login. The password is still verified. It only activates in a non-production environment, and only when explicitly configured.

⛔ Never enable this in production

The bypass is force-disabled whenever COOKIE_SECURE=true. Even with the flag on and the correct secret, production staff logins always require OTP. A startup warning is logged if the flag is set in a production environment.

Quick start

In your local docker.env / .env (where COOKIE_SECURE=false):

# enable the bypass and choose a secret (local dev only)
DEV_SKIP_OTP=true
DEV_BYPASS_SECRET=my-local-dev-secret

Then log in, sending the secret as the X-Dev-Bypass header:

curl -i -X POST http://localhost:3000/twhp/api/authentication/login \
  -H 'Content-Type: application/json' \
  -H 'X-Dev-Bypass: my-local-dev-secret' \
  -d '{"username":"eval01","password":"correct-password"}'

You get cookies (Authentication + Refresh) and { "message": "login successful", "user": {…} } in one step — no OTP email, no challenge.

How it works

The bypass fires only if every one of these is true (fail-closed — any miss falls back to the normal flow):

1DEV_SKIP_OTP === trueenv (master switch)
2COOKIE_SECURE === false (not production)env (production signal)
3DEV_BYPASS_SECRET is set and non-emptyenv (the secret)
4X-Dev-Bypass header equals DEV_BYPASS_SECRET (constant-time compare)request
5username / password already verifiedgetAutheticatedAccount()
request POST /authentication/login { username, password, header X-Dev-Bypass } │ ├─ verify credentials ───────────► wrong password → 401 (header ignored) │ ├─ isDevOtpBypass(header) ? │ flag on && !production && secret set && timingSafeEqual(header, secret) │ ├─ requiresOtp(role) === false OR bypass === true │ └─► issue cookies, { message, user } ← bypass lands here │ └─ otherwise → mint Redis challenge + send 2fa-otp email └─► { twoFactorRequired, challengeId, email }

Configuration

VariableTypeDefaultMeaning
DEV_SKIP_OTPbooleanfalseMaster switch. Must be true for the bypass to be possible.
DEV_BYPASS_SECRETstring""The shared secret. The X-Dev-Bypass header must equal this. Empty ⇒ bypass impossible.
COOKIE_SECUREboolean(required)Existing var. true = production ⇒ bypass hard-disabled. false = dev.

✅ Safe defaults

With nothing set, DEV_SKIP_OTP defaults to false and the secret to empty — the feature is inert. Both must be deliberately configured for it to work. A malformed DEV_SKIP_OTP (anything other than true/false) makes the app refuse to boot.

Usage & examples

Enable (local)

# docker.env — local development only
COOKIE_SECURE=false
DEV_SKIP_OTP=true
DEV_BYPASS_SECRET=my-local-dev-secret

Log in without OTP

curl -i -X POST http://localhost:3000/twhp/api/authentication/login \
  -H 'Content-Type: application/json' \
  -H 'X-Dev-Bypass: my-local-dev-secret' \
  -d '{"username":"doed01","password":"correct-password"}'

# → 200  Set-Cookie: Authentication=… ; Set-Cookie: Refresh=…
# → { "message": "login successful", "user": { "id": 2, "role": "DOED", … } }

Disable

# either remove the secret…
DEV_BYPASS_SECRET=
# …or flip the master switch off
DEV_SKIP_OTP=false

⚠️ The header is not an auth bypass

It skips only the OTP factor. A wrong password still returns 401, with no cookies, regardless of the header. The header alone grants nothing.

Security guarantees

Production hard-block

When COOKIE_SECURE=true, the bypass returns false unconditionally — flag and header are ignored.

Fail-closed

Unset flag, empty secret, or missing/mismatched header ⇒ normal flow. The default posture is deny.

Constant-time compare

The secret is matched with crypto.timingSafeEqual (length-guarded) — no timing/length oracle.

Credentials first

getAutheticatedAccount runs before the bypass is even evaluated; a bad password short-circuits to 401.

No secret leakage

DEV_BYPASS_SECRET is never logged, never returned, never written to Redis.

Observability

Every fired bypass logs a warn with { accountId, username, role } — visible if it ever activates by accident.

Implementation map

If you need to read or change the feature, the whole thing is four small touch-points:

FileWhat lives there
src/config.tsDEV_SKIP_OTP + DEV_BYPASS_SECRET with optionalEnvBoolean / optionalEnv validation.
src/index.tsOne-time startup warn when the flag is set with COOKIE_SECURE=true.
src/service/authentication.tsisDevOtpBypass(presentedSecret) — the pure, fail-closed decision (guards → constant-time compare).
src/routes/authentication/index.tsReads x-dev-bypass, ORs the bypass into the existing non-OTP /login branch, logs OtpBypassed.

The decision helper, in full:

isDevOtpBypass: (presentedSecret: string | undefined): boolean => {
  if (!env.DEV_SKIP_OTP) return false;       // master switch off
  if (env.COOKIE_SECURE) return false;       // production hard-block
  const secret = env.DEV_BYPASS_SECRET;
  if (!secret) return false;                 // no secret → impossible
  if (!presentedSecret) return false;
  const presented = Buffer.from(presentedSecret);
  const expected = Buffer.from(secret);
  if (presented.length !== expected.length) return false; // guard length throw
  return timingSafeEqual(presented, expected);
}

Rationale for using COOKIE_SECURE as the production signal is recorded in memory-bank/bolts/017-dev-otp-bypass/adr-4-cookie-secure-as-production-signal.md.
