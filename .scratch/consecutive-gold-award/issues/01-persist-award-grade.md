# 01 — Record every award in an Awards table at finalize

**Status:** ready-for-agent
**Category:** enhancement

## Agent Brief

**Category:** enhancement
**Summary:** Introduce an `Awards` table as the permanent record of what each factory has won, written once per Cover at finalization, so later fiscal years can read a past Grade instead of recomputing it.

**Current behavior:**
The Grade is computed on demand wherever it is needed — the factory Score
Report, the three staff Score Report lists, and the finalize response — by
running the grade calculator over the Cover's Answers. Nothing is written to the
database. Per ADR-0001 this was deliberate: a past Cover is simply re-scored
under whatever rules are deployed today.

**Desired behavior:**
A new table records one award per factory per fiscal year. When finalization
moves a Cover to `finished`, the Grade it computes is written there, once, and
never recomputed for that Cover. Every read path returns the stored value.

The table is the permanent forward-going record, not a migration artifact. It is
also the table issue 04 seeds with imported FY2566 history, so a row may exist
with no originating Cover.

A Grade exists only for a `finished` Cover — the existing finished-only guard
(intent `011-finished-cover-reward-guard`) is unchanged. A Cover that is
`in_review` still reports a null Grade, and the finished test remains the latest
`coverLogs` row by greatest serial `id`, per ADR-0010.

Finalize is already the only writer of `finished` (ADR-0012); it becomes the only
writer of an award row for a real Cover.

**Key interfaces:**

A Grade enum type in the database whose values are exactly the wire values —
`consec-gold`, `gold`, `silver`, `certificate`, `joined`. `GradeSchema` must then
derive from the generated base schema rather than stay hand-declared, per the
CLAUDE.md rule that DTOs compose from `BaseXxxSelect/Insert/Update`. This issue
adds the enum with the four current values; issue 02 adds `consec-gold`.

An `Awards` table carrying:

- the factory, referencing `Factories.account_id`
- the fiscal year, as the **Common Era** year the fiscal year ends in — the
  convention in `src/schema/fiscal-year.ts`. FY2566 (1 Oct 2022 – 30 Sep 2023)
  is stored as `2023`
- the Grade
- the originating Cover, **nullable** — null for imported history
- an awarded-at timestamp

**These names are a contract.** The manual backfill SQL in issue 04 depends on
them. Use exactly: table `"Awards"`; columns `factory_id`, `fiscal_year`,
`grade`, `cover_id`, `awarded_at`; enum type `"Grades"`; and a unique constraint
on (`factory_id`, `fiscal_year`) that `ON CONFLICT` can target. Rename any of
them and the backfill SQL must change in the same PR.

Constraints that carry real weight:

- unique on (factory, fiscal year) — one award per factory per year
- unique on the Cover reference — Postgres treats nulls as distinct, so many
  imported rows coexist while each real Cover is awarded at most once
- a check that the fiscal year is between `FISCAL_YEAR_MIN` and
  `FISCAL_YEAR_MAX` (2000–2100). Writing a Buddhist Era year such as 2566 by
  mistake is the obvious corruption path, and this catches it on the first bad
  write
- the Cover reference restricts deletion. An award is a public record and must
  not be silently orphaned

Other interfaces:

- The award's fiscal year is **the Cover's** fiscal year, not the current one. A
  past-year Cover can be finalized after rollover (ODPC and DOED past-year
  authority, and the 31-day Factory grace window). Use the existing
  `fiscalYearOfCover` in the evaluator review service, or `getFiscalYearOf` on
  the enrolment date. Never `getFiscalYear()` with no argument.
- `computeGrade()` keeps its signature and stays pure. Finalize writes the result.
- The award row is written in the same transaction that writes the `finished`
  `coverLogs` row, so a Cover cannot be `finished` without an award.
- Read paths — the single factory Score Report, the shared staff Score Report
  list implementation, and the finalize response — return the stored Grade.
- The scoring breakdown stays computed on demand. Only the Grade is stored.

**Acceptance criteria:**
- [ ] Finalizing a Cover writes exactly one `Awards` row; its grade equals what
      `computeGrade()` returned for that Cover at that moment.
- [ ] The row carries the Cover's own fiscal year in Common Era, and references
      the originating Cover.
- [ ] A FY2026 Cover finalized on 5 Oct 2026 writes `fiscal_year = 2026`, not
      2027.
- [ ] A Cover that is `in_review` has no `Awards` row and every read path reports
      `grade: null`.
- [ ] Re-reading a `finished` Cover returns the stored Grade unchanged after the
      grade rules in code have changed.
- [ ] An Answer edited after finalization does not change the stored Grade.
- [ ] A second finalize of the same Cover cannot write a second award row.
- [ ] Two factories may hold awards in the same fiscal year; one factory may not
      hold two awards in the same fiscal year.
- [ ] Writing a Buddhist Era year such as 2566 is rejected by the database.
- [ ] `ScoreReportSchema` and both finalize route response schemas are unchanged
      in shape — same field, same nullability.
- [ ] The staff Score Report lists issue no per-item query for the Grade
      (no N+1 reintroduced; see ADR-0011).
- [ ] The isolated test suite passes.

**Out of scope:**
- Changing any grade threshold or gate — issue 02.
- The `consec-gold` enum value — issue 02 adds it.
- The enrolment lockout — issue 03.
- Importing FY2566 — issue 04.
- Persisting the scoring breakdown.
- Backfilling award rows for Covers already `finished` - issue 04 does that by
  hand, and it must run before this code serves reads, or every FY2569 Score
  Report shows a null Grade.
- Any change to what `in_review` or province-scoped readers may see (ADR-0013).

## Notes

ADR-0001 must be amended or superseded here, not left stale. Its recorded
consequence — *"old covers are automatically re-scored with the new rules…
historical scores are not audited separately"* — becomes false, because two award
decisions now audit historical Grades. Per CLAUDE.md a business-rule change
updates the affected guide and ADR in the same change.

Covers finalized before this change hold no award row. Covers finalized after it
do. Two Covers with identical Answers can therefore report different Grades once
issue 02 lands. This is deliberate — it is the point of storing the Grade — but
it will read as a defect to anyone comparing them, so the release note must say
so.

This change is released **after** the auditors finish FY2569, so finalize writes
no award row until FY2570. Every row that exists on release day comes from the
seed in issue 04. That is why the discontinuity above is harmless in practice -
the seed captures FY2569's true grades before the new gate goes live.

`enroll.integration.test.ts` deletes enrolments during cleanup. Once the Cover
reference restricts deletion, that teardown must clear awards first.
