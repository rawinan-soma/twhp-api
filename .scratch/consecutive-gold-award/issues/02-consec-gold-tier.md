# 02 — Add the consec-gold tier and settle the gold gate

**Status:** ready-for-agent
**Category:** enhancement
**Depends on:** 01

## Agent Brief

**Category:** enhancement
**Summary:** Add `consec-gold` as the top award tier, gated on a gold-tier award three fiscal years earlier, and narrow the `gold` special-question gate.

**Current behavior:**
There are four grades, evaluated strictly top-down: `gold`, `silver`,
`certificate`, `joined`. The calculation depends only on the Cover's own
Answers; no other fiscal year is consulted.

The `gold` special gate is **already in conflict, and the conflict is recorded.**
`CONTEXT.md` states the gate as *"full score (live choice `"3"`) on every
question where `special` is `1` or `3`"*, and its Question glossary entry repeats
it. The deployed grade calculator instead gates on every Question with
`special > 0` — all eleven, including the five at `special == 2`.

The conflict is listed in three places, all of which name the code as
authoritative and the question as unsettled:

- `docs/business-rules.md` BR-23 — *"code's gold gate includes `special=2`;
  `CONTEXT.md` says only 1 or 3. Code is authoritative."*
- `docs/domain-model.md`, current-code-authority table — *"Gold requires full
  score on every `special > 0` Question"* against *"`CONTEXT.md` says only
  `special` 1 or 3"*.
- `docs/technical-debt.md` TD-06 — lists *"the Gold `special` set"* among the
  conflicts a product owner must settle, and marks the item
  **Required before handover: Yes**.

So the `gold` change in this issue is **not a new rule**. It settles a recorded
conflict in favour of the documented intent, and brings the code to what
`CONTEXT.md` has said all along.

**Desired behavior:**
Five grades, still strictly top-down, first match wins:

| Grade | Gate |
| --- | --- |
| `consec-gold` | the `gold` gate, **AND** every `special == 2` Answer scored `"3"`, **AND** the factory held a gold-tier award in fiscal year FY − 3 |
| `gold` | every category > 80%, total >= 90%, **AND** every `special == 1` and `special == 3` Answer scored `"3"` |
| `silver` | every category > 60% AND total >= 80% |
| `certificate` | total >= 60% |
| `joined` | otherwise |

Two consequences of settling the `gold` gate, stated so they are not
rediscovered during implementation:

- Against the **deployed code**, `gold` becomes easier to reach, because the five
  `special == 2` Questions stop gating it. A Cover that finishes `silver` under
  the code running today can finish `gold` after this change. Against
  **`CONTEXT.md`**, nothing changes at all. Both statements are true; the first
  is what operations will observe.
- The `consec-gold` special gate — `special` in `{1, 2, 3}` — is exactly the gate
  the deployed code applies to `gold` today. So the effect of this issue is that
  the current code behaviour moves up one tier and acquires a history check,
  and `gold` drops to the gate `CONTEXT.md` specifies.

"Held a gold-tier award in FY - 3" means the `Awards` table (issue 01) holds a
row for that factory, for the fiscal year three back, whose grade is `gold` or
`consec-gold`. The row's origin does not matter — it may come from a finalize or
from the FY2566 import (issue 04).

Any of the following means the factory is not consec-gold and falls through to
`gold`:

- no `Awards` row for that factory in FY - 3
- a row graded `silver`, `certificate` or `joined`

Only FY - 3 is consulted. FY - 1 and FY - 2 are not checked, and their absence is
not a disqualification - a gold winner is locked out of those years by design
(issue 03).

An `n/a` Answer does not satisfy a special gate. The gate requires the literal
choice `"3"`, so `n/a` blocks the tier even though it is excluded from the
percentages. This matters for the `special == 2` Question *ขยายการดำเนินงาน
โครงการฯ ไปยังหน่วยงานอื่น*, the only special Question with an `n/a` option
(*"เข้าร่วมเป็นปีแรก"*). A first-year factory is correctly not eligible for
consec-gold.

**Reading the Awards table is one owner's job.** Issues 02 and 03 both ask it a
gold-tier question. Write a single resolver that answers "did this factory hold a
gold-tier award in fiscal year Y", used by both, in the same spirit as
`coverStatus.ts` owning latest-Cover-status resolution under ADR-0010. A second
ad-hoc query over `Awards` is a review failure.

**Key interfaces:**
- The database Grade enum and the derived `GradeSchema` gain `"consec-gold"`.
  Both finalize route response schemas reference the shared schema and inherit
  it. Adding a value to a Postgres enum is not reversible by `db:push` alone -
  confirm the change applies against a disposable database first.
- `computeGrade()` needs the FY−3 result as an **input**, not a lookup it
  performs itself — it must stay pure and synchronous, and the staff list paths
  must be able to resolve the whole page's history in one batched query rather
  than per item (ADR-0011). Give it a parameter carrying "this factory held gold
  in FY − 3", resolved by the caller.
- The fiscal-year helper currently returns only the current window and has no
  notion of an offset. It needs to express "the window N fiscal years back".
  Per CLAUDE.md, fiscal-year boundaries are never hand-rolled at the call site.
- The result-notification email maps each grade to a Thai label. `consec-gold` is
  **"รางวัลเชิดชูเกียรติและประกาศนียบัตรระดับประเทศ ประเภท โล่ทองต่อเนื่อง"**, following the
  form the `gold` and `silver` labels already use (…ประเภท โล่ทอง / โล่เงิน). The
  plaque name itself is โล่ทองต่อเนื่อง.

**Acceptance criteria:**
- [ ] A Cover meeting the gold gate, with every `special == 2` Answer at `"3"`,
      whose factory stored `gold` in FY − 3, grades `consec-gold`.
- [ ] The same Cover grades `gold` when the FY − 3 grade is `silver`, is null,
      or has no Cover or no enrolment in that year.
- [ ] A FY − 3 grade of `consec-gold` also qualifies, not only `gold`.
- [ ] A Cover with a `special == 2` Answer at `"2"` grades `gold`, not
      `consec-gold`, given the FY − 3 history.
- [ ] A Cover with an `n/a` on a `special == 2` Question grades `gold`, not
      `consec-gold`.
- [ ] A Cover with a `special == 1` or `special == 3` Answer below `"3"` cannot
      reach `gold` however high its percentages.
- [ ] A Cover with every `special == 1` and `special == 3` Answer at `"3"`, a
      `special == 2` Answer at `"1"`, all categories above 80% and a total of at
      least 90% grades `gold` — the case that was `silver` before this change.
- [ ] Boundary cases still hold: a category at exactly 80.0% is not gold; at
      exactly 60.0% is not silver; totals use `>=`.
- [ ] Grade remains null for any Cover that is not `finished`.
- [ ] The staff score-report lists resolve FY−3 history for a page in a bounded
      number of queries that does not grow with page size.
- [ ] `ScoreReportSchema` accepts `"consec-gold"` and still rejects an unknown
      grade such as `"platinum"`.
- [ ] `CONTEXT.md`'s Grade table and Question glossary entry need no correction
      for the `gold` gate - the code now matches what they already say.
- [ ] BR-23 in `docs/business-rules.md` no longer records a `special=2`
      discrepancy, and its rule text states the settled ladder.
- [ ] The `Gold requires full score on every special > 0 Question` row is removed
      from the conflict table in `docs/domain-model.md`.
- [ ] TD-06 in `docs/technical-debt.md` records the Gold `special` set as
      settled, in the same form as its 2026-09-02 update for ADR-0012.
- [ ] The finished-result email renders the consec-gold Thai label, not the raw
      grade key.
- [ ] The isolated test suite passes.

**Out of scope:**
- The enrolment lockout — issue 03.
- Backfilling FY2566 — issue 04.
- Any change to `silver`, `certificate` or `joined`.
- The evidence rule that gives `special == 3` Questions one file per choice —
  unrelated to grading and unchanged.
- A six-year tier. The doc text on Question *ส่งเสริมสุขภาพและป้องกันโรคไม่ติดต่อ
  เรื้อรัง* implies one may follow; write the lookback so a second tier is a new
  gate rather than a rewrite, but do not build it.

## Notes

A new ADR should record the five-tier ladder and the FY-3 rule, and should state
plainly that the `gold` gate was settled in favour of `CONTEXT.md` rather than
changed. Per CLAUDE.md, a business-rule change updates the affected guide and ADR
in the same change - here that is BR-23, the `docs/domain-model.md` conflict
table, and TD-06.

Settling this closes one of the conflicts TD-06 marks **Required before
handover**. The remaining TD-06 items - standard auto-credit acceptance, N/A
eligibility, assignment meaning, and the absent transition matrix - are untouched
by this issue and stay open.

Operational note for release: because the deployed code gates `gold` on
`special > 0`, some already-`finished` Covers would grade differently under the
new gate. They will not change, because issue 01 stores the Grade at finalize and
no past Cover is ever re-scored. Covers finalized after this change use the new
ladder. This is a deliberate discontinuity, not a defect, and the release note
should say so.



Current special-Question distribution in `seed_data/questions.json` — 3 at
`special == 1` (ids 6, 9, 25), 5 at `special == 2` (ids 7, 38, 39, 40, 41),
3 at `special == 3` (ids 14, 21, 37). All four Outcome Questions are
`special == 2`, so under this change the Outcome category is all-or-nothing for
consec-gold specifically. Treat these as data, not constants — the gates read
the `special` column.
