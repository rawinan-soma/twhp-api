# 04 — Backfill award history, FY2566–FY2569

**Status:** ready-for-human
**Category:** enhancement
**Depends on:** 01, 02 (schema only — the `Awards` table and the `Grades` enum including `consec-gold`)

## Why this is ready-for-human

No application code is written for this issue. The maintainer runs it by hand
against production, once, because:

- FY2566–FY2568 results come from records only the maintainer holds.
- FY2569 can only be backfilled after the auditors finish on **30 Sep 2026**,
  and it is a one-shot production write that belongs in the release step.

The FY2569 SQL is provided in `../backfill-fy2569.sql`.

## Part A — FY2566, FY2567, FY2568: gold winners, by hand

No Covers, Answers or enrolments exist for these years. Insert one row per gold
winner:

```sql
INSERT INTO "Awards" (factory_id, fiscal_year, grade, cover_id) VALUES
  (1024, 2023, 'gold', NULL),   -- FY2566
  (1187, 2024, 'gold', NULL)    -- FY2567
ON CONFLICT (factory_id, fiscal_year) DO NOTHING;
```

- `factory_id` is `Factories.account_id`. Insert only factories that exist in
  the system; skip the rest.
- `fiscal_year` is **Common Era**: FY2566 = `2023`, FY2567 = `2024`,
  FY2568 = `2025`. Writing 2566 is rejected by the database check.
- Only golds. No other grade is recorded for these years.
- `cover_id` is always `NULL`.

## Part B — FY2569: every grade, by SQL

FY2569's Covers are in the database and their Score Reports are live. Every
finished Cover needs a row at its real grade, not only the golds — otherwise
issue 01 makes its Score Report return `grade: null`.

`../backfill-fy2569.sql` computes each grade from the database with the rule
that was deployed while the auditors worked — the same result the Score Report
and the finalize email already showed:

| Grade | Rule |
| --- | --- |
| `gold` | every category > 80%, total >= 90%, every `special > 0` Answer is `"3"` |
| `silver` | every category > 60%, total >= 80% |
| `certificate` | total >= 60% |
| `joined` | otherwise |

Plus one upgrade: a `gold` whose factory holds a gold-tier award in FY2566 is
written as `consec-gold`. That is what makes consec-gold valid in FY2569. The
FY2569 gold rule already requires every `special == 2` Answer to be `"3"`, so
the consec-gold special condition is met automatically.

Percentages reproduce `scoreHelpers.ts` exactly — float division then
`Math.round`, `n/a` excluded, an empty category scores 0. Current Cover status
is the latest `CoverLogs` row by greatest serial `id` (ADR-0010).

The file runs in five steps:

1. **Three-year check.** Expect 0 rows. A row means a factory won gold twice
   within three fiscal years.
2. **Duplicate check.** Expect 0 rows. A factory with two finished FY2569 Covers
   would lose one.
3. **Preview.** Read-only. Compare a sample of factories against the live Score
   Report before inserting.
4. **Insert** inside `BEGIN`. Check the `RETURNING` rows, then `COMMIT` or
   `ROLLBACK`. Re-running inserts nothing new.
5. **Verify.** The FY2569 award count must equal the FY2569 finished Cover count.
6. **Late finalizations.** Run again after 31 Oct 2026 — see below.

The FY2569 window in the SQL is `[2025-09-30 17:00, 2026-09-30 17:00)` UTC —
midnight 1 October in Bangkok, the same boundary as `getFiscalYear(2026)`.
`enroll_date` is stored in UTC because PostgreSQL runs on UTC.

**The SQL has not been run.** The local database was down when it was written.
Step 3 is the check: if any previewed grade differs from what the Score Report
shows for that factory today, stop and report it before step 4.

## Run order

1. **30 Sep** — auditors finish FY2569. Every Cover finalized.
2. **Push the schema** from issues 01 and 02 (`Awards` table, `Grades` enum).
   The change only adds things, so the old API keeps working.
3. **Part A** — insert FY2566–FY2568 golds.
4. **Part B** — run `backfill-fy2569.sql`, steps 1 to 5.
5. **Deploy the new API code.** It now reads grades from `Awards`, which is full.
6. **1 Oct** — FY2570 opens. From here finalize writes every award.

Step 3 must come before step 4, because FY2569 consec-gold reads FY2566.
Step 4 must come before step 5, or FY2569 Score Reports show `null` until it
runs.

The window is tight — FY2570 opens the next day. The programme manager already
gatekeeps FY2570 enrolment, so a short delay in step 5 does no harm.

## Decision: release after 30 Sep, accept late finalizations

A FY2569 Cover can still be finalized after 30 Sep: a Factory has a 31-day grace
window (to 31 Oct 2026) to finish a prior-year Cover, and ODPC and DOED can
finalize past years at any time. The maintainer chose to release after 30 Sep
anyway.

Consequence, accepted: a FY2569 Cover finalized **after** the release gets its
award from the new code, under the **new** gold rule, not the rule the auditors
used. The backfill never sees it, because the Cover was not `finished` when
the backfill ran.

SQL step 6 lists these awards. Run it after 31 Oct 2026 and review each one.

## Acceptance criteria

- [ ] Every FY2566–FY2568 gold winner that exists in `Factories` has one row,
      grade `gold`, `cover_id` NULL.
- [ ] Step 1 and step 2 return 0 rows.
- [ ] Step 3 grades match the live Score Report for a sample of factories,
      including at least one of each grade present.
- [ ] Step 5 counts match.
- [ ] Step 6 is run after 31 Oct 2026 and each late award is reviewed.
- [ ] A FY2569 gold factory with a FY2566 gold row is recorded `consec-gold`.
- [ ] After step 5 of the run order, every FY2569 Score Report shows the same
      grade as before the release, except consec-gold upgrades.

## Out of scope

- Creating accounts for factories not in the system.
- Grades below gold for FY2566–FY2568.
- Any application code.
