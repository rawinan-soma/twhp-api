# Observability: logs, traces, metrics and alerts

Status: ready-for-agent
Category: enhancement
Triaged: 2026-09-25

## Problem

The API and the email worker are unobservable. There are no metrics, no traces and no central
logs. Nothing connects an API request to the email job it queues. The only health check always
answers "Ready to work!!", even when PostgreSQL, Redis or MinIO is down. A stale worker once dropped
the safety-officer `cc` from verdict emails on staging for two weeks without anyone noticing (see
`.scratch/verdict-email-safety-officer/`).

`docs/technical-debt.md` TD-12 records this gap. This PRD covers TD-12's telemetry, health and alerting
parts. It does not cover backup, recovery or graceful shutdown.

## Decisions (settled during triage)

| # | Decision |
|---|----------|
| 1 | The monitoring stack is defined in this repo's `docker-compose.yaml`, next to the app. |
| 2 | Traces go to **Grafana Tempo**, not Jaeger. Logs go to Loki, metrics to Prometheus, and all three are viewed in Grafana. Grafana Alloy is the single collector. |
| 3 | The stack runs under its own opt-in `observability` Compose profile. |
| 4 | **Production always runs with `--profile observability`.** Alerting is in scope. |
| 5 | **Strict redaction.** No secrets (tokens, cookies, authorization headers, passwords, OTPs, presigned signatures) and no personal data (email addresses, names, phone numbers, national/tax IDs, client IP) appear in logs, spans or metric labels. People are referred to only by internal IDs such as `userId` and `factoryId`. |
| 6 | Retention: **logs 90 days, traces 7 days, metrics 30 days.** |
| 7 | Grafana binds to `127.0.0.1` on the host and is reached only through an SSH tunnel. Each person gets their own Grafana account, and anonymous access is off. No nginx route. |
| 8 | Alerts go to a **Discord** channel through a webhook. |
| 9 | Eight starter alerts (see below). Thresholds are tuned after two weeks in production. |
| 10 | Log timestamps are ISO 8601 with the Bangkok offset, e.g. `2026-09-25T14:30:05.123+07:00`, in both API and worker. |
| 11 | Grafana dashboards, alert rules, contact points and data sources are **provisioned from files in the repo**. The Discord webhook URL is a secret and is not in the repo. |
| 12 | Health splits into `/health/live` (process up) and `/health/ready` (PostgreSQL, Redis and MinIO reachable). `/health` stays as an alias of live. |
| 13 | Extra exporters: `node_exporter` and MinIO's built-in Prometheus endpoint only. |
| 14 | Every request is logged as one light line: method, path without query string, route template, status, duration, `userId`, `trace_id`. No user-agent, full URL, query string or client IP. |
| 15 | 100% of traces are kept, with no sampling. |
| 16 | Every API response carries `X-Request-Id` set to its trace ID. |
| 17 | Staging runs the stack only when `--profile observability` is added. Its alerts go to a test Discord channel. |
| 18 | The worker stays a compiled binary. Its traces come from BullMQ's native telemetry plus hand-written spans. |
| 19 | Metrics use `prom-client`, served on an internal-only port (default `9464`) by the API and by the worker, and scraped by Prometheus. |
| 20 | Bun and Elysia are pinned to exact versions before any telemetry code lands. |
| 21 | We write our **own** request-span hook instead of using `@elysiajs/opentelemetry`. See ADR-0014. |
| 22 | The API ignores inbound `traceparent` headers and always starts a new trace. |

Approved dependencies: `@opentelemetry/api`, `@opentelemetry/sdk-trace-node`,
`@opentelemetry/exporter-trace-otlp-proto`, `@opentelemetry/resources`,
`@opentelemetry/semantic-conventions`, `@opentelemetry/instrumentation-pg`, `bullmq-otel@1.3.0`
(pinned, because later versions need a newer BullMQ) and `prom-client`. Container images, each pinned
to a version: `grafana/grafana`, `grafana/loki`, `grafana/tempo`, `prom/prometheus`, `grafana/alloy`,
`prom/node-exporter`. **Not** approved: `@elysiajs/opentelemetry`. Any other package needs a fresh
ask.

## Starter alerts

| # | Alert | Fires when |
|---|-------|------------|
| 1 | API down | API metrics target unreachable for 2 min |
| 2 | Worker down | Worker metrics target unreachable for 5 min |
| 3 | Email jobs failing | Any email job failed in the last 15 min |
| 4 | Email queue stuck | The oldest waiting email job is older than 10 min |
| 5 | Server errors | 5xx responses > 1% of requests over 10 min |
| 6 | Slow API | p95 request duration > 2 s over 10 min |
| 7 | Dependency down | PostgreSQL, Redis or MinIO unreachable from the API for 2 min |
| 8 | Disk almost full | Host root filesystem > 85% used |

## Research findings that shaped the design (2026-09-25)

Probed under Bun 1.3.6 and 1.4.2:

- The OpenTelemetry `pg` instrumentation works under Bun when loaded by preload in a source-run
  process. It does not work inside a `bun build --compile` binary.
- `ioredis`, `node:http` via ESM import and Bun's `fetch` are **not** auto-instrumented under Bun.
  MinIO, SMTP and fetch calls need hand-written spans.
- BullMQ 5.71's `telemetry` option with `bullmq-otel` carries one trace ID from `queue.add` through
  the worker's processing, including inside the compiled binary. It needs a global W3C propagator.
- `@elysiajs/opentelemetry` 1.4.11 copies every request header onto spans, including the
  `Authentication`/`Refresh` cookies and `authorization`. It also pins `@opentelemetry/sdk-node ^0.200`.
- `prom-client` default metrics work under Bun. GC duration stays empty, and heap numbers describe
  JavaScriptCore's heap.
- A pino `mixin` reading the active span adds `trace_id`/`span_id`. `@bogeychan/elysia-logger`'s default
  `formatters.log` throws mixin fields away on its own request line, so that formatter must be overridden.
- Bun is unpinned: a developer laptop ran 1.3.6 while `oven/bun:1` resolved to 1.4.2.

## Out of scope

- Browser/frontend monitoring.
- Backups, restore, RPO/RTO. TD-12 stays open for these.
- Graceful shutdown.
- Email delivery reliability: outbox, deterministic job IDs, retry policy (TD-11). Telemetry will
  *show* failures, not fix them.
- Business/reporting dashboards.
- Exposing Grafana through nginx, Cloudflare Access or any public route.
- `cAdvisor`, `postgres_exporter`, `redis_exporter`.
