# 08 — Dashboards and the eight alerts, provisioned, to Discord

Status: ready-for-agent

## Agent Brief

**Category:** enhancement
**Summary:** Provision Grafana dashboards, the eight starter alert rules, and a Discord contact point from files in the repo.

**Current behavior:**
After issue 04, Grafana has data sources but no dashboards, alert rules or contact points.

**Desired behavior:**
- **Contact point `discord`**: Discord integration, webhook URL from `DISCORD_WEBHOOK_URL` in
  `observability.env`, never in the repo. The default notification policy routes everything to it.
  Messages include the alert name, the `env` label, a one-line summary, and a link to the relevant
  dashboard.
- **Alert rules**, Grafana-managed, provisioned from files, every rule labelled with `env`:

  | # | Alert | Condition |
  |---|-------|-----------|
  | 1 | API down | `up{job="api"} == 0` for 2 m |
  | 2 | Worker down | `up{job="worker"} == 0` for 5 m |
  | 3 | Email jobs failing | `increase(twhp_email_jobs_total{outcome="failed"}[15m]) > 0` |
  | 4 | Email queue stuck | `twhp_email_queue_oldest_waiting_seconds > 600` |
  | 5 | Server errors | 5xx share of `http_server_request_duration_seconds_count` > 1% over 10 m, and at least 20 requests in that window, to avoid firing on 1 of 3 at night |
  | 6 | Slow API | p95 of `http_server_request_duration_seconds` > 2 s over 10 m |
  | 7 | Dependency down | `twhp_dependency_up == 0` for 2 m, per dependency |
  | 8 | Disk almost full | root filesystem used > 85% from `node_exporter` |

  Also: "no data" on rules 1, 2 and 7 counts as firing, and each rule has a `summary` annotation in
  plain language.
- **Dashboards**, provisioned and read-only in the UI (edit → export → commit):
  - *API overview:* request rate, error rate, p50/p95/p99 by route, dependency status, and a Loki
    panel of recent error lines linked to traces.
  - *Email queue:* job states, oldest waiting age, completed/failed rate by job name, worker up.
  - *Host:* CPU, RAM, disk, and MinIO storage used.
- **Staging:** the same files. Staging's `observability.env` points `DISCORD_WEBHOOK_URL` at a test
  channel. Document this in `docs/deployment.md`.
- `docs/troubleshooting.md` gains a short "Alert fired: what to check first" entry per alert, so the
  person on Discord knows the next step.

**Key interfaces:**
- Grafana provisioning files: `alerting/` (rules, contact points, policies) and `dashboards/`.
- `observability.env.example` gains `DISCORD_WEBHOOK_URL`.

**Acceptance criteria:**
- [ ] On a fresh `down -v && up` with the profile, all three dashboards and all eight rules exist
      without any manual step.
- [ ] Stopping the worker container fires "Worker down" to the Discord test channel within about
      6 minutes. Restarting it resolves the alert.
- [ ] Forcing an SMTP failure (bad SMTP host in dev) fires "Email jobs failing".
- [ ] `grep -ri "discord.com/api/webhooks" observability/` returns nothing.
- [ ] Every rule's `summary` annotation is present, and a troubleshooting entry exists per rule.

**Out of scope:**
- Threshold tuning. That happens after two weeks in production and is tracked as a follow-up.
- On-call rotation or paging.
- Business dashboards.
