# 09 — Production rollout

Status: ready-for-human
Category: enhancement
Blocked by: 01–08 (see Preconditions)
Model: none (human task)

## Why this is not for an agent

It needs SSH/VPN access to the production VM, production secrets (Grafana admin password, Discord
webhook, MinIO credentials), pushing the production image, and a judgement call on when to restart
production. An agent cannot do any of these.

## Preconditions

- Issues 01–08 are merged to `main`, and verified together on dev or staging with
  `--profile observability`.
- A production Discord channel exists, and you have its webhook URL.
- A separate test channel is used for staging (issue 08).

## Step by step

Replace `<version>` with the release tag, e.g. the `package.json` version, and `<vm>` with the
production host.

### A. On your laptop: build and push the image

The production worker is a compiled binary inside the image, so the image must be rebuilt. A restart
alone keeps the old worker (see `CLAUDE.md`).

```bash
git checkout main && git pull
docker build -t rawinan/twhp-elysia-api:<version> -t rawinan/twhp-elysia-api:latest .
docker push rawinan/twhp-elysia-api:<version>
docker push rawinan/twhp-elysia-api:latest
```

### B. On the VM: check room and record the rollback point

```bash
ssh <user>@<vm>          # through the VPN
cd <deploy dir>

free -h                  # want ≥ 2 GB available for the new containers
df -h /                  # want ≥ 20 GB free: 90 days of logs plus metrics and traces
docker compose --profile production images   # note the current image ID for rollback
cp docker.env docker.env.bak-$(date +%F)
cp docker-compose.yaml docker-compose.yaml.bak-$(date +%F)
```

Also confirm Docker's own log rotation is on, so container log files don't fill the disk while
Alloy tails them:

```bash
cat /etc/docker/daemon.json   # expect "log-opts": {"max-size": "...", "max-file": "..."}
```

If it's missing, add something like `{"log-driver":"json-file","log-opts":{"max-size":"50m","max-file":"5"}}`.
Restarting Docker restarts every container, so do it in a quiet window, or set it per service in
Compose instead.

### C. On the VM: update files and secrets

1. Bring the new `docker-compose.yaml` and the `observability/` directory onto the VM, the same way
   you deliver the compose file today (e.g. `git pull`).
2. Create the stack's secrets file:
   ```bash
   cp observability.env.example observability.env
   chmod 600 observability.env
   nano observability.env
   ```
   Set a strong `GF_SECURITY_ADMIN_PASSWORD`, set `DISCORD_WEBHOOK_URL` to the **production**
   channel, and fill the MinIO scrape credentials. Use the key names listed in the example file.
3. Add the app-side keys to `docker.env`:
   ```
   OTEL_EXPORTER_OTLP_ENDPOINT=http://alloy:4318
   DEPLOYMENT_ENV=production
   ```
4. Validate before starting anything:
   ```bash
   docker compose --profile production --profile observability config > /dev/null && echo OK
   docker compose --profile production --profile observability config | grep -n "published"
   ```
   The only new published port must be Grafana's, bound to `127.0.0.1` with port `3001`.

### D. On the VM: start the monitoring stack, then the app

```bash
docker compose --profile production --profile observability pull
docker compose --profile production --profile observability up -d \
  alloy loki tempo prometheus grafana node-exporter
docker compose --profile production --profile observability ps     # all running/healthy

docker compose --profile production --profile observability up -d --force-recreate api worker
docker compose --profile production --profile observability ps
```

From now on, **the production start command is always**
`docker compose --profile production --profile observability up -d`. Update any script, cron or
systemd unit that starts production.

### E. On the VM: check the app

```bash
docker compose --profile production exec api \
  bun -e "fetch('http://localhost:3000/twhp/api/health/ready').then(r=>r.text()).then(console.log)"
# expect {"status":"ready","checks":{"postgres":"up","redis":"up","minio":"up"}}

ss -ltnp | grep 3001      # must show 127.0.0.1:3001, never 0.0.0.0:3001
```

From your laptop, **without** a tunnel, `curl -m 5 http://<vm-ip>:3001` must fail.

### F. From your laptop: open Grafana and set up people

```bash
ssh -N -L 3001:127.0.0.1:3001 <user>@<vm>
```

1. Open `http://localhost:3001` and log in as `admin` with the password from `observability.env`.
2. **Administration → Users and access → Users → New user**: one account per person (2–3 people),
   role **Viewer**, or **Editor** for anyone who edits dashboards. Don't share the admin login.
3. Check each data source works:
   - **Explore → Prometheus**, query `up`. Every target (`api`, `worker`, `node-exporter`, `minio`)
     should be `1`.
   - **Explore → Loki**, query `{service="api"}`. Recent lines should have ISO `+07:00` times and
     `trace_id`.
   - Use the site once in a browser, copy the `X-Request-Id` response header from DevTools → Network,
     and paste it in **Explore → Tempo**. The request trace appears, and if that request queued an
     email, the worker part is in the same trace.
4. Check the redaction: in Loki, search `{service=~"api|worker"} |= "@"` over the last hour. Expect
   no email addresses. Also run a search for `Refresh=`, which should return nothing.
5. **Alerting → Contact points → discord → Test.** The message should arrive in the production
   Discord channel.
6. *Optional, in a quiet window:* `docker compose --profile production stop worker`, wait about 6
   minutes for "Worker down" in Discord, then `start worker` and watch it resolve. Queued emails wait
   in Redis meanwhile.

### G. Rollback

- **Telemetry misbehaving but the app is fine:**
  `docker compose --profile production --profile observability stop alloy loki tempo prometheus grafana node-exporter`.
  The app keeps working; trace export fails silently.
- **App problem after the new image:** restore `docker.env.bak-*` and redeploy the previous image
  tag noted in step B, then `up -d --force-recreate api worker`.

### H. Two weeks later

Review which alerts fired and whether any was noise. Adjust thresholds in the repo's provisioning
files, then redeploy. Record the new values in the PRD's alert table.

## Acceptance criteria

- [ ] All Prometheus targets are `up` in production.
- [ ] A real request's `X-Request-Id` resolves to a trace in Tempo, with linked logs in Loki.
- [ ] The Discord test notification is received in the production channel.
- [ ] Grafana is unreachable from outside the VM without the SSH tunnel.
- [ ] Each of the 2–3 people has their own Grafana login.
- [ ] Production start instructions everywhere include `--profile observability`.
