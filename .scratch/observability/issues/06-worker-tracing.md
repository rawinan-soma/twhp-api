# 06 — Worker tracing: BullMQ propagation, SMTP and DB spans

Status: ready-for-agent
Category: enhancement
Blocked by: 05 (trace context, propagator and scrubbing rules)
Model: Opus 5.5, medium effort (BullMQ propagation and OTel import order in a compiled binary)

## Agent Brief

**Category:** enhancement
**Summary:** Carry the API request's trace into the email worker through BullMQ's native telemetry, and add hand-written spans for SMTP sends and the worker's DB work.

**Current behavior:**
Email jobs are enqueued by the API and processed by a separate worker process. In production the
worker is a `bun build --compile` binary. Nothing links a job to the request that queued it.

**Desired behavior:**
- The same queue and worker are constructed with BullMQ's `telemetry` option, using
  `new BullMQOtel("twhp")` from `bullmq-otel@1.3.0`, pinned. Later versions require a newer BullMQ.
  This applies to the queue used by the API and to the worker.
- The worker process has its own telemetry bootstrap: `service.name=twhp-worker`, the same context
  manager, W3C propagator, exporter rule (export only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set) and
  redaction rules as issue 05. It is **imported first** by the worker entrypoint rather than
  preloaded, so it works inside the compiled binary.
- A job enqueued during an API request is processed in the **same trace**: API SERVER span → BullMQ
  add → BullMQ process → worker spans.
- Hand-written spans in the worker:
  - `smtp.send`: job name, recipient **count**, accepted/rejected counts, SMTP `messageId`. No
    addresses, subject or body. Status is error when the relay throws or rejects every recipient.
  - A span around each DB read in the worker, e.g. the validation-reminder query, named by purpose
    (`db.pending_factories`). Automatic `pg` spans don't work in the compiled binary (ADR-0014).
- Worker pino logs (issue 02) carry `trace_id`/`span_id` from the active span.
- The daily repeatable reminder job starts its own root trace. It has no parent request.

**Key interfaces:**
- The shared queue definition and the worker construction: the `telemetry` option.
- A worker telemetry bootstrap module imported first by the worker entrypoint.
- The email-sending helper wrapped in `smtp.send`.

**Acceptance criteria:**
- [ ] A test with an in-memory exporter and a disposable Redis enqueues a job inside an active span.
      The worker's `process` span and `smtp.send` span share that span's trace ID.
- [ ] No exported worker span attribute contains `@`.
- [ ] `docker build` succeeds, and running `./worker-bin` against the dev stack with the
      `observability` profile shows an API request → email job trace in Tempo.
- [ ] With `OTEL_EXPORTER_OTLP_ENDPOINT` unset, the worker runs and sends email normally.
- [ ] `package.json` pins `bullmq-otel` to exactly `1.3.0`.
- [ ] The isolated test suite passes, and `biome check src` reports no new findings.

**Out of scope:**
- Upgrading BullMQ.
- Retry, dead-letter or idempotency changes (TD-11).
- Running the worker from source in production. It stays compiled.
- Worker metrics (issue 07).
