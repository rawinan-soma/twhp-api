# Safety officer does not receive the verdict email when finalize rejects a Cover

Status: closed (resolved 2026-09-04 — stale deploy, no code defect)
Category: bug
Reported: 2026-09-04 (frontend team, verbally)
Reporter: frontend

## Report

> When frontend reject the cover in finalized, they only got the email in Factory email,
> not in Safety officer email.

Maintainer follow-up (2026-09-04): the enroll's `safety_officer_email` **is not null**, and the
address still received nothing.

## Triage Notes

**What we've established so far:**

- The reported path is `evaluatorReviewService.finalize` (`src/service/evaluator-review.ts:401`).
  A hard reject sets `newCoverStatus = "in_progress"` (`:629`) and enqueues exactly one
  `verdict-result-in-progress` job (`:720`).
- Recipients are built once, before the branch (`:704-712`): `to = Accounts.email` (factory login,
  NOT NULL + unique), `cc = Enrolls.safety_officer_email`. The cc is dropped **only** when it is
  null/blank or byte-identical to the account email — deliberate, so nobody is addressed twice.
- `src/worker/email.ts:149-158` forwards `cc: data.cc` to `transporter.sendMail` on the
  in-progress template. The finished template does the same at `:114-125`.
- Shipped in 35bbc3c (2026-08-20), present on `main` and `dev`.
- **Verified at HEAD**: `bun test src/service/evaluator-review.verdict.integration.test.ts`
  against a disposable DB — 30 pass / 0 fail. Two assertions cover this exact path:
  `:465` (reject → in_progress) and `:407` (finished) both assert
  `payload.cc === "safety_finalize@test.com"`. **The enqueue side is correct.**
- The failure is therefore downstream of the queue, in the worker → SMTP relay
  (`mailrelay.uc-workd.com:587`) → mailbox leg, or in the stored value of the address itself.
- Could not reproduce locally: the local `twhp` database holds 0 enrolls, and
  `twhp-workers-dev` has logged no verdict email in the last 72h. The frontend team tested
  against a deployment this session cannot see.

**Two code defects found while tracing, worth fixing regardless of the root cause:**

1. `src/worker/email.ts` discards the `sendMail` result. Nodemailer returns per-recipient
   `info.accepted` / `info.rejected`; if the relay accepts the `to` RCPT and rejects the `cc`
   RCPT, the send is silently recorded as a success. There is currently no way to tell a
   dropped cc from a never-sent one — exactly the observability we need here.
2. `CreateEnrollWithFilesSchema.safetyOfficerEmail` is `t.Optional(t.String())`
   (`src/schema/enroll.ts:61`) — no `format: "email"`, no trim — while the *update* schema at
   `:117` does enforce `format: "email"`. An address captured at enroll creation can be
   malformed or whitespace-padded and will be rejected by the relay at RCPT time while the
   factory's copy still lands. This matches the reported symptom.

**What we still need from you (@reporter):**

1. Which environment did you test on — production, staging, or a local `docker compose` stack?
   (The local stack on this machine has an empty database, so it wasn't that one.)
2. The `coverId` (or factory account ID + fiscal year) you finalized, so the exact enroll row
   can be read. Specifically needed: the raw value of `Enrolls.safety_officer_email` including
   any leading/trailing whitespace, and the factory's `Accounts.email` — if the two are equal,
   the cc is dropped by design and nothing is broken.
3. Did the **factory** copy arrive with the safety officer visible in its Cc: header? The
   officer is cc'd on the factory's message, not sent a separate email. If the header shows the
   address, the problem is delivery/filtering at the officer's mailbox, not this codebase.
4. Has the officer's spam/junk folder been checked?
5. If you have access: the relay log line for that message, showing which RCPT TO commands were
   accepted.
6. Design question, separate from the bug: do you expect the safety officer to receive a
   **separate email addressed to them**, rather than a cc on the factory's? That is an

## Comments

### 2026-09-04 — defect 1 fixed (observability)

> *This was generated by AI during triage.*

`src/worker/email.ts` now routes all five senders through a `sendAndLog(label, options)` wrapper
that logs nodemailer's per-recipient `info.accepted` / `info.rejected`, plus `messageId` and the
relay's `response` string. A partial rejection logs at `console.error` and is deliberately **not**
thrown — throwing would make BullMQ retry the job and re-deliver to recipients the relay already
accepted.

This does not fix the reported symptom; it makes the next occurrence diagnosable. On the next
finalize-with-reject, the worker log will carry one of:

- `[verdict-result-in-progress] sent { accepted: [factory, officer] }` — the relay took both, so
  the loss is at the officer's mailbox (filtering/spam), not in this system.
- `[verdict-result-in-progress] relay rejected 1 recipient(s) { rejected: [officer] }` — the relay
  refused the address; read it back from `Enrolls.safety_officer_email` and check its format,
  which points at defect 2 below.
- `accepted: [factory]` with no officer in either list — the cc never left this codebase, meaning
  `safety_officer_email` was null or equal to the account email at read time.

Verification: biome clean on the file; `tsc --noEmit` error count unchanged at 57 (all
pre-existing, in unrelated test files); isolated suite 201 pass / 0 fail.

**Defect 2 (no `format: "email"` or trim on `CreateEnrollWithFilesSchema.safetyOfficerEmail`) is
still open** — deliberately left until the log above says whether a malformed address is actually
the cause. Fixing it now would also raise the question of what to do with rows already stored.

### 2026-09-04 — staging evidence: the API side is exonerated

Maintainer supplied the staging job (tested on **staging**, not local):

```
job 176  2026-09-04 07:12:03  verdict-result-finished
{"email":"himopox881@mediseat.com","cc":"rawinan.soma@gmail.com",
 "grade":"silver","factoryNameTh":"บริษัท วังน้อย เบเวอเรช จำกัด (สำนักงานใหญ่)"}
```

The `cc` key is present and correct, and the job completed. **`finalize` and the queue are doing
their job** — the address was read, deduped correctly, and handed to the worker. The loss is at the
worker → relay → mailbox leg. The cc mailbox reports nothing in inbox or spam.

**Two things this changes:**

1. The job name is `verdict-result-finished`, **not** `verdict-result-in-progress`. The finalize
   that produced it had no hard reject. So the original report ("when frontend reject the cover")
   is not what was actually tested, and the symptom is not specific to the reject path — it
   affects the cc on both templates. The repro line at the top of this issue is misleading.
2. Sender-auth is unlikely to be the cause. `ddc.mail.go.th` publishes
   `v=spf1 include:_spf.uc-workd.com include:_spf.google.com -all`, and `_spf.uc-workd.com`
   resolves to the relay's IP ranges, so SPF should pass. DMARC at `mail.go.th` is `p=none`, so
   Gmail will not reject on policy. A silent Gmail discard is therefore not the leading theory.

**Incidental finding (not the cause):** `SMTP_STARTTLS` and `SMTP_SECURE` are validated in
`src/config.ts:66-67` but read nowhere — `createTransport` (`src/worker/email.ts:37`) passes only
host, port and auth. On port 587 nodemailer still negotiates STARTTLS opportunistically, so mail
is normally encrypted, but it is not *required*: a relay that fails to advertise STARTTLS would get
credentials and message bodies in cleartext without any error. Worth wiring up separately.

**Next step:** get the per-recipient SMTP response with a direct relay test from the staging host
(`docker exec twhp-workers-dev bun -e ...` with `logger: true, debug: true`), which prints each
`RCPT TO` result without needing the logging change deployed.

### 2026-09-04 — ROOT CAUSE: stale worker image on staging

> *This was generated by AI during triage.*

**Resolved. No code defect — a stale deployment.**

Two facts closed it:

1. A direct relay test from the staging host (`nodemailer` with `logger/debug`, addressing the
   same two mailboxes) showed the relay accepting **both** recipients — `RCPT TO` returned
   `250 2.1.5 Ok` for the factory address *and* for the cc — queued as one message, and **both
   mailboxes received it, cc included**. So the relay, Gmail, SPF and the `cc` field were never
   the problem.
2. `docker exec twhp-workers-dev grep -n "cc: data.cc" /app/src/worker/email.ts` on staging
   returned **nothing**. The running worker predated 35bbc3c (2026-08-20) and its
   `sendMail` options had no `cc` key at all, so it dropped the address on the floor.

The API was enqueueing a correct payload (job 176 carried `cc`) into a worker that could not read
it. `worker-dev` has **no source bind mount** — it bakes code in at `build` (`target: build`), so
`docker compose up -d` without `--build` keeps serving the old image indefinitely, even while
`api-dev` is rebuilt around it. That is what produced the "factory gets mail, safety officer
doesn't" split.

**Fix applied by the maintainer:** `docker compose --profile staging up -d --build worker-dev`.
Confirmed resolved.

**Rejected along the way — worth recording so it isn't retried:**

- *Switch `cc` to `to` on both templates.* Would have changed nothing. Nodemailer builds the SMTP
  envelope from `to` + `cc` + `bcc` alike, so both addresses already got their own `RCPT TO`; only
  the header differs. The apparent "`to` works, `cc` doesn't" signal was confounded — the two
  addresses differed in header position *and* in mailbox provider (disposable temp-mail vs Gmail).
- *Sender-auth / Gmail silent discard.* SPF passes and DMARC is `p=none`; the relay test
  delivered to Gmail on the first attempt.

**Still open, tracked here:**

- **Defect 2** — `CreateEnrollWithFilesSchema.safetyOfficerEmail` (`src/schema/enroll.ts:61`) has
  no `format: "email"` and no trim, while the update schema at `:117` does. Not the cause of this
  incident, but a malformed address stored at enroll time would fail at RCPT with no trace.
- **`SMTP_STARTTLS` / `SMTP_SECURE`** are validated in `src/config.ts:66-67` and read nowhere.
  The relay does advertise and negotiate STARTTLS (confirmed in the transcript above), so mail is
  encrypted in practice — but not by requirement.
- **The logging change from earlier in this issue is uncommitted** on `dev`. It is what would have
  made this a one-minute diagnosis instead of a multi-step hunt: with it deployed, the worker log
  would have read `accepted: [factory]` with the officer in neither list, pointing straight at the
  worker rather than at the relay.
