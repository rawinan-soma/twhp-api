## Confirmed With User

### Duplicated fiscal-year range constants

**Finding.** `FISCAL_YEAR_MIN` / `FISCAL_YEAR_MAX` (2000–2100) were declared independently in
`src/utils.ts` and `src/schema/fiscal-year.ts`. They agreed, but nothing enforced that.

**Why it mattered.** The two bounds sit on either side of the same request. The schema rejects an
out-of-range year with a 400; the resolver throws `RangeError` on the same condition. Had they
diverged, a year the schema accepted would reach the resolver and throw — turning a clean validation
400 into an unhandled 500.

**Resolution** (user-selected): `src/utils.ts` now imports both constants from
`src/schema/fiscal-year.ts`, which is the single source of truth.

- No import cycle: `src/schema/fiscal-year.ts` imports only from `elysia`.
- Trade-off accepted: a utility module now depends on a schema module. The alternative direction was
  rejected because `src/utils.ts` constructs a Redis client at import time
  (`export const redisConnector = utilities().createRedisConnector()`), and pulling that into every
  route that imports the schema would be worse.

Verified after the change: exactly one declaration of each constant remains in `src/`.
